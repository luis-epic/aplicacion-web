# Revocación de permisos y creación de proyectos aún incompletas (seguimiento)

La revisión limitada a los cuatro P1 previos encuentra dos P1 todavía abiertos. Los permisos reducidos durante una sesión no se reflejan por completo en el área activa, y el alta de proyectos continúa dependiendo de `clients.read` en la interfaz pese a que la API no lo exige. **Watch for:** **confirmed** — una revocación de `*.read` deja visibles datos ya cargados del área activa; **confirmed** — `projects.manage` no basta para crear proyectos desde el portal sin `clients.read`.

## High-level view

El filtrado de navegación oculta áreas sin su permiso `*.read`, pero no invalida el área seleccionada. Cuando un refresh devuelve permisos reducidos, `PortalWorkspace` conserva la selección y los datos cargados; tras el 403 de recarga, vuelve a mostrarlos.

La carga principal de Proyectos ya no depende de `/clients`, pero el formulario de alta se oculta con `projects.manage && clients.read`. `POST /projects` solo exige `projects.manage`, por lo que la UI restringe una capacidad que el servidor autoriza.

## La revocación de lectura no cierra el área activa ni elimina sus datos

**Confirmed (P1).** `PortalWorkspace` conserva `area`, `users`, `clients`, `projects` y `reports` cuando `PortalApi` entrega una sesión renovada. `visibleAreas` oculta el botón ya no autorizado, pero el contenido se renderiza solo en función de expresiones como `area === 'clients'`, sin volver a comprobar `clients.read`.

La actualización de sesión intenta recargar el área; el servidor rechaza la lectura, pero la colección anterior no se vacía. Un usuario al que se le retire `users.read`, `clients.read`, `projects.read` o `fieldReports.read` continúa viendo los datos previos hasta cambiar de área o recargar. La sesión renovada debe moverlo a una zona permitida, limpiar el estado del recurso revocado y aplicar el permiso también al renderizado del contenido.

## El alta de proyectos todavía exige un permiso que la API no requiere

**Confirmed (P1).** `ProjectForm` solo aparece cuando coinciden `projects.manage` y `clients.read`, mientras `POST /projects` está protegido únicamente por `projects.manage`. Un usuario autorizado para administrar proyectos no puede crear uno desde el portal si no puede listar clientes.

La UI necesita una fuente de `clientId`, pero no debe redefinir silenciosamente la autorización. Hace falta una búsqueda de clientes limitada al flujo de proyectos y autorizada por `projects.manage`, o declarar y aplicar `clients.read` como requisito también en la API y el modelo de permisos.
